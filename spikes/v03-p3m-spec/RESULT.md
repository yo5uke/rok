# V3：P3M の仕様

実施：2026-10-05（P3M 2026.09.0、公開版 packagemanager.posit.co）
再現：`./probe.sh`（取得物は `out/`）

## 結論

**成功。** 次の情報は、すべて機械的に取得できる：スナップショットの URL、OS・ディストリビューション・R の版ごとのバイナリの URL、索引のチェックサム、システム依存の情報。

ただし、要件定義書の想定と異なる点が2つある。いずれも「設計への影響」に修正案を書いた。

- Linux の索引にはチェックサムがない
- ソースの SHA-256 は、今の版しか API から得られない

## URL の形式

| 用途 | URL |
|---|---|
| ソースの索引 | `/cran/<日付>/src/contrib/PACKAGES.gz` |
| Linux のバイナリ | `/cran/__linux__/<binaryURL>/<日付>/src/contrib/<pkg>_<ver>.tar.gz` |
| Windows のバイナリ | `/cran/<日付>/bin/windows/contrib/<x.y>/PACKAGES.gz`、`<pkg>_<ver>.zip` |
| macOS のバイナリ | `/cran/<日付>/bin/macosx/<macos_urls[x.y][arch]>/contrib/<x.y>/PACKAGES.gz`、`<pkg>_<ver>.tgz` |
| 環境の一覧 | `/__api__/status`：`distros`（ディストリビューションと `binaryURL` の対応、arch）、`r_versions`（バイナリを作る R のマイナー版：4.2〜4.6、3.6）、`macos_urls` |
| スナップショットの日付 | `/__api__/repos/cran/transaction-dates`（1989件、2017-10-10〜） |
| パッケージの情報 | `/__api__/repos/cran/packages/<pkg>`：`checksum`、`archived`（過去の版と公開日） |
| システム依存 | `/__api__/repos/cran/sysreqs?all=false&pkgname=<a>&pkgname=<b>&distribution=ubuntu&release=24.04` |

- **ディストリビューションの対応**：`/etc/os-release` の ID と VERSION_ID を、`distros` の `distribution` と `release` に照らすと、`binaryURL` が得られる（ubuntu 24.04 → `noble`、redhat 9 → `rhel9` など）。
- **日付**：一覧にない日付は、その直前のスナップショットになる（2017-10-11 → 2017-10-10 と同じ内容）。最初のスナップショットより前の日付と、最新より後の日付は 404 になる（`invalid transaction`）。
- **ある版を取得できる日付**：その版が最新だった日付の URL からしか取得できない。新しい日付の URL で古い版を指定すると 404 になる。
- **取得の経路**：ダウンロードは `rspm-sync.rstudio.com`（S3＋CloudFront）への 307 リダイレクトになる。日本からは、1リクエストに 0.8 秒ほどの遅延がある。

## Linux のバイナリ

- **索引**：Linux の索引（`__linux__/noble/...`）の中身は、ソースの索引とバイト単位で同一である。どのパッケージにバイナリがあるかは、索引からは分からない。
- **版の判定**：配信する中身は User-Agent で決まる。`R (4.6.1 x86_64-pc-linux-gnu x86_64 linux-gnu)` の形で、**パッチ版まで含めた R の版**と arch を送るとバイナリが返る。`R (4.4 …)` や `curl/8` ではソースが返る。
- **種類の判定**：応答ヘッダーで判定できる。`x-package-type: binary|source` と `x-package-binary-tag: 4.6-noble`（arm64 なら `4.6-noble-arm64`）が付く。HEAD でも同じヘッダーが返るので、ダウンロードせずに判定できる。
- **古い日付**：その時点で存在しない R の版にはソースが返る。2025-01-02 の data.table 1.16.4 は、R 4.4 ではバイナリ、R 4.6 ではソースだった。提供範囲の詳細は V4 で調べる。
- **中身の目印**：バイナリの DESCRIPTION には `Built: R 4.6.0; x86_64-pc-linux-gnu; …` が入る。

## チェックサム

| 対象 | 索引のチェックサム | 実体との照合 |
|---|---|---|
| ソース（P3M の索引） | **なし**（CRAN 本家の索引には `MD5sum` がある） | — |
| Linux のバイナリ | **なし**（索引がソースと同一のため） | — |
| Windows・macOS のバイナリ | `Hash` 欄 | バイナリのファイルの **MD5** と一致 |
| API の `checksum` | — | **CRAN 本家のソース tar.gz の SHA-256** と一致。P3M が配るソースとは一致しない |

- P3M が配るソースの tar.gz は、DESCRIPTION に `Repository: RSPM` が加わっている。そのため、CRAN 本家のファイルとはバイト単位で異なる（MD5・SHA-256 とも不一致）。
- API の `checksum` が返るのは、**今の版だけ**である。過去の版（`archived` にある版）を `?version=` で指定すると、空文字が返る。
- CDN の ETag は、ファイルの MD5 と一致した（単一パートのアップロード）。ただし配信元と同じ経路から来る値なので、転送中の破損の検出にしか使えない。

## システム依存

- 1回の要求で、複数のパッケージと、その依存の分までまとめて返る（sf を指定すると s2・units の分も返る）。
- 返るのは **ビルド用の -dev パッケージ**（libgdal-dev など）と、`apt-get install -y …` のコマンドである。RHEL 系では、`pre_install`（epel-release）も返る。

## 注意点

- 推奨パッケージ（boot、class など15件）は、P3M と CRAN のどちらの索引にも、`Path: 4.7.0/Recommended` 付きの2件目の記録がある（R-devel に同梱される版）。索引の解析では、`Path` 付きの記録を除く必要がある。
- Windows・macOS の索引は、R のマイナー版ごとに別で、ソースより件数が少ない。2026-10-01 時点で、ソースは 25300 件、Windows 4.6 は 25140 件、macOS 4.6 arm64 は 22611 件だった。索引にないパッケージは、ソースからのビルドになる。
- macOS の `macos_urls` が空文字の版（x86_64 の 4.0〜4.2）は、`bin/macosx/contrib/<x.y>` を指すと考えられる（未確認）。

## 設計への影響

1. **バイナリの判定（フェーズ1）**：Linux では、同期の前に HEAD を並列に送り、パッケージごとにバイナリがあるかを判定する。この結果で「軽い」と「重い」を分ける。結果は（日付・パッケージ・版・R のマイナー版・ディストリビューション・arch）をキーにして永久にキャッシュする。User-Agent には、ロックにある R のパッチ版を入れる。
2. **ダウンロード時の照合（第9章）**：Windows・macOS では `Hash`（MD5）と照合する。Linux とソースは、索引にチェックサムがないので HTTPS のみとする。要件の「索引に載っていれば照合する」と食い違いはない。
3. **ロックのハッシュ（第7章・第9章）**：「OS 共通のソース tar.gz の SHA-256」には、API の `checksum`（CRAN 本家のファイルのハッシュ）を使える。ただし、過去の版は API から得られない。CRAN のアーカイブから tar.gz を取得して計算する必要がある → **要件の判断が必要**（報告で選択肢を示す）。
4. **スナップショットの日付（第5章 init の既定値）**：最新より後の日付は 404 になる。そのため、その日の分が公開される前に今日の日付を指定すると、404 になると考えられる（この時間帯での実測はしていない）。したがって「作成日」ではなく、「作成時点で公開済みの最新の日付」を記録する必要がある → **要件の文言の修正が必要**。
5. **日付の混在（第7章）**：古い版は、その版が最新だった日付の URL から取る。ロックには、パッケージごとの日付が必須になる（要件どおり）。
6. **renv からの移行（第7章）**：P3M のスナップショットは 2017-10-10 からしかない。それより古い renv.lock は、日付を推定できない（V10 で扱う）。
7. **システム依存（第7章・status）**：API の -dev パッケージは、ビルド用の一覧である。バイナリを使うだけなら、実行時のライブラリで足りる。そのため、-dev パッケージの有無で判定すると過剰に「不足」となる。不足の判定方法（展開した `.so` に対する `ldd` など）は、0-2（V2）で検証する。
8. **索引の解析**：`Path` 付きの記録を除く。Linux の索引はソースと共通なので、日付ごとに1回取得すればよい。

## 決定（2026-10-05、要件定義書に反映済み）

- 影響3：案B を採る。ハッシュは、API から得られる場合（今の版）と、ソースを取得した場合だけ記録する。CRAN のパッケージのソースは CRAN から取得する。Linux のバイナリのダウンロード時の検証は、HTTPS のみとする（第7章・第9章）
- 影響4：日付は、P3M が公開済みの最新の日付を既定とする。ユーザーが指定した日付は、実在する日付に解決して表示・記録する（第5章・第7章）
- 影響7：実行時ライブラリの判定は、V3b として第13章に追加した
