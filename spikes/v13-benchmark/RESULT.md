# V13：速度のベンチマーク（Linux 分、比較対象の基準値）

実施：2026-10-05
再現：`./bench.sh`（測定。v01 の `run.sh` を先に実行しておく）→ `python3 summarize.py`（集計）
rok は未実装なので、今回は比較対象（renv・pak・rv・uvr）の測定と、測定用スクリプトの整備までとする。

## 方法

各ツールで、プロジェクトごとに次の順で測った。

1. **準備（参考値）**：キャッシュを消してからロックを作り、ライブラリに入れる。renv は `install` → `snapshot`、pak は `lockfile_create` → `lockfile_install`、rv は `sync`（＋`activate`）、uvr は `init` → `add`。
2. **S4 キャッシュなし（cold、3回）**：ツールのキャッシュとプロジェクトのライブラリを消し、ロックから入れる。renv は `restore`、pak は `lockfile_install`、rv は `sync`、uvr は `sync`。
3. **S3 キャッシュあり（warm、5回）**：プロジェクトのライブラリだけを消し、ロックから入れる。
4. **S2 依存の解決（5回、renv を除く）**：索引をキャッシュ済みの状態で、ロックを作り直す。pak は `lockfile_create`、rv はロックを外して `plan`、uvr は `lock`。renv には、解決だけを行う操作がない。
5. **S1 起動（10回）**：同期済み（変化なし）のプロジェクトで `Rscript -e 'invisible(0)'` にかかる時間を測る。基準は、空の `.Rprofile` を置いた空のディレクトリ。差を「上乗せ」とする。pak には起動フックがないので除く。renv は、有効にしたプロジェクトを別に作って測った。

## 測定上の注意

- **時計**：最初は `date` で測ったが、WSL2 で壁時計が飛び、pak の cold が 0.2 秒と出た（pak 自身の表示も `-100ms`）。そのため、単調時計（`mono.py`、Python の `time.monotonic_ns`）で測った。
- **隔離**：ツールのキャッシュ・設定・HOME は、すべて `out/` に向けた。uvr はパッケージの実体を `~/.uvr/packages` に置き、`UVR_CACHE_DIR` では変わらない。そのため HOME も `out/home` に向け、uvr の cold ではそれも消した。試行の段階で、ホームに `~/.uvr` と `~/.cache/rv` が作られたため削除した。
- **renv の snapshot**：推奨パッケージ（lattice、nlme）は R 本体のライブラリにあるので、`snapshot(library = …)` の事前チェックに落ちる。`force = TRUE` で通した（renv の通常の使い方でも、推奨パッケージはロックに入らない）。
- **パッケージ数の違い**：ツールによって、推奨パッケージをプロジェクトのライブラリに入れるかどうかが違う。uvr は、補助の `uvr` パッケージも入れる。

## 読み取れること

- **S1・S2・S3**：rv が最も速く、uvr が続く。どちらも、要件の目標（100 ms、1 秒、2 秒）をすでに満たしている。rok も、この水準を下回らないことが最低条件になる。
- **S4**：pak が最も速い（medium 13.7 s、gis 19.8 s）。uvr がそれに続く。rok の S4 の目標は、この環境では「medium で 14 秒前後以下」が目安になる。
- **rv の S4 が遅い理由**：rv はキャッシュありでは最速だが、キャッシュなしでは pak の約 2.5 倍かかった。最初の試行のログでは、2パッケージのインストール自体は 2.5 秒で、全体の 19 秒の大半は索引の取得と準備だった。取得の並列度や索引の扱いが効いていると考えられる（詳細は未調査）。
- **pak の S3 が S4 に近い理由**：キャッシュがあっても、R と pak の子プロセスの起動、メタデータの確認に毎回数秒かかる。
- **ばらつき**：S2 の pak と uvr には、外れ値（12〜16 秒）が出た。メタデータの更新が走った回と考えられる。中央値で比べるのが適切である。
- **uvr の弱点**：キャッシュの実体（`~/.uvr/packages`）を消すと、それへのリンクで組んだプロジェクトのライブラリが壊れた。その状態で `uvr sync` は `Failed to move staged package` で失敗し、自分では直せなかった（S1 の測り直しで発見）。

## 設計への影響

1. **速度の目標値（第9章）**：S1・S2・S3 の目標は、比較対象（rv・uvr）がすでに満たしている。そのため、目標値をより厳しくする余地がある。S4 は、pak・uvr の値（この環境で medium 14〜19 秒）を基準にする。目標値の確定は、rok の実装後の測定（1-9）で行う。
2. **リンクの壊れの検出と修復（第5章 status・sync）**：rok もキャッシュへのリンクでライブラリを組む。キャッシュが消えたり壊れたりした場合に、切れたリンクを status で検出し、sync で取り直せる必要がある（uvr の失敗例）。
3. **時間の測り方**：WSL2 では壁時計が飛ぶ。rok が表示する所要時間や、ベンチマークは単調時計で測る。
4. **測定の仕組み**：`bench.sh` に、rok を5つ目のツールとして加えられる（`setup`、`install`、`solve` に rok の分岐を足す）。
