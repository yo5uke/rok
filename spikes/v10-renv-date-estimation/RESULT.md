# V10：renv からの移行での日付の推定

実施：2026-10-05（P3M 2026.09.0）
再現：`python3 run.py`

## 結論

**成功。** 「ある版が CRAN の最新だった期間」は、P3M のパッケージ API（`/__api__/repos/cran/packages/<pkg>`）から、1パッケージ1回の要求で求められる。API の現行版と `archived`（過去の版と公開日時）を使う。

検証では、6つの日付で30件ずつ（計180件）抜き出したパッケージが、すべて求めた区間に入った。区間の共通部分から推定した日付の範囲にも、6件とも正解の日付が入った。

## 方法

1. パッケージごとに API を1回呼び、各版の公開日時を得る（30件を16並列で約2秒）。
2. 版 v の区間を [v の公開日時, 次の版の公開日時) とする。
3. スナップショットの日付 T（UTC の0時）に v が載るのは、**公開日時 < T ≤ 次の版の公開日時** のときとみなす。
   - 実測：2024-07-17 15:50 に公開された Rcpp 1.0.13 は、07-17 の分にはなく、07-18 の分に載った。2025-01-12 公開の 1.0.14 も、翌日の 01-13 に載った。
4. ロックの全パッケージの区間の共通部分が、全版が揃う日付の範囲になる。その範囲を、実在するスナップショットの日付（`transaction-dates`）に当てはめる。
5. 共通部分が空のとき（古いままのパッケージが混じるとき）は、日付ごとに「区間に入るパッケージの数」を数え、最大の日付を選ぶ。

## 検証結果

| 正解の日付 | 区間に入った | 推定した範囲 | 正解を含む |
|---|---|---|---|
| 2018-05-30 | 30/30 | 2018-05-30（1日） | ○ |
| 2020-03-02 | 30/30 | 2020-02-24〜2020-03-05（4日） | ○ |
| 2022-09-01 | 30/30 | 2022-08-24〜2022-09-02（8日） | ○ |
| 2024-06-03 | 30/30 | 2024-05-22〜2024-06-28（38日） | ○ |
| 2025-11-03 | 30/30 | 2025-05-09〜2026-01-14（216日） | ○ |
| 2026-09-01 | 30/30 | 2026-09-01〜2026-09-13（13日） | ○ |
| 混在（2024-06-03 の25件＋2023-06-01 の5件） | 最大25/30 | 2024-04-20〜2024-06-25（67日） | ○ |

## 注意点

- **スナップショットの日付は毎日ではない**：2017年は25日、2018年は102日、2024年以降は年に約330日。一覧にない日付は、直前のスナップショットに読み替えられる。
- **最初のスナップショットは 2017-10-10**：それより古い renv.lock は、P3M の日付に当てはめられない。
- **公開日時のない版**：ごく古い版（例：Rcpp 0.6.x）は、公開日時が null である。区間を作れないので、「版の記録なし」として扱う。
- **範囲の幅**：抜き出した件数が少ないと、範囲は広くなる。実際の renv.lock は数十〜数百件なので、狭まると見込める。

## 設計への影響

1. **日付の推定（第7章「renv からの移行」）**：P3M の履歴を日付ごとに取り寄せる必要はない。パッケージごとの API で足りる。100件のロックでも数秒で終わる。公開済みの版の区間は変わらないので、キャッシュできる。
2. **範囲のどの日を選ぶか**：範囲内のどの日でも、ロックの版はすべて最新なので、ロックの再現の結果は同じである。違いが出るのは、後から `add()` するパッケージの版だけである。どの日を選ぶかは 2-7 で決める（案：範囲の最初の日、または最後の日）。
3. **V4 の調査にも使った**：「日付 T で最新の版」を求める同じ関数で、V4 の各日付の版を決めた。
